# 用户请求、需求与验收

[requests.json](requests.json) 是用户请求台账，需求 ID 用于任务、提交和交接引用；产品完成状态仍只以 [PROJECT_STATE.md](../PROJECT_STATE.md) 为准。

## 来源和覆盖范围

- 当前上下文可见的请求、确认和约束已逐条登记。`original_text` 为请求原文或明确标记的长文索引摘要，`capture_scope` 说明保存范围。
- 引用对话“改用Git管理项目”只有截断预览；全文读取工具不可用，不能宣称已收齐所有历史对话。该缺口保存在台账 coverage 中。
- 旧 AGENTS.md 长文保存为 [历史文件快照](sources/2026-10-08-user-agents-draft.md)，不是完整聊天导出，也不是当前有效规则。
- `historical_requirement_index` 按 DECISIONS.md 建立历史追溯；它是决定索引，不是假造的用户逐字聊天。待决与已采纳分别保留。
- 助手曾建议的语音、外部 LLM 等不能仅因出现在建议里就当作已批准功能；“上市”未进一步澄清，不自动解释为证券上市或公开部署授权。

## 后续每一条请求如何保存

1. 收到新需求、纠正、取消或范围确认，先追加一个递增 `REQ-xxx`，保留用户原意和来源。已有请求的原文、ID 和来源不静默改写；纠正/替代用新请求并注明关联 ID。
2. 原始日期未知写 null；记录本次观察日期。长文可以放 sources/ 并引用，注明全文/摘录/摘要；私人数据和密钥先脱敏，不复制进 Git。
3. 为可执行项写清输入、状态、输出、失败情况、验收条件和不包含范围；本次准备的验收见下表。复杂业务仍需任务卡，不用聊天里的“看起来完成”替代验收。
4. 写明相关文件、决定/契约、责任人和证据路径。状态与验证证据可追加更新，旧来源保留；未运行的检查写未验证。
5. 一项请求包含多件任务时使用其 ID 下的验收编号或另建关联项。实现前读取 AGENTS.md / DEVELOPMENT.md，需要接口变化先登记提案。

台账状态 `RECORDED` 仅表示已记录；`IMPLEMENTED_WITH_EVIDENCE` 需有相关证据；`IMPLEMENTATION_PENDING_VERIFICATION` 表示正在实施；`PARTIAL_WITH_EVIDENCE` 表示已有交付但仍有明确缺口。历史状态不能代替当前项目状态。

## 本轮需求验收（REQ-010）

输入：引用对话可见预览、现有仓库、当前明确请求。状态：开发准备；不启动新 Sprint。输出：可运行说明、请求台账、契约基线、分工及预检。

| 编号 | 需求与可观察验收 | 实现 / 验证入口 |
| --- | --- | --- |
| A1 | 新开发者能按步骤装依赖，启动两个服务；地址、环境变量、测试命令对应实际配置 | 根 README；预检 --smoke、本轮交接 |
| A2 | 可见请求各有 ID、来源和验收；缺失历史明确标为不完整，后续纠正也追加保存 | requests.json；预检台账引用检查 |
| A3 | 现有两份 Schema 与核心 TS 镜像有固定基线；篡改被拒绝，换行差异被允许 | schemas/BASELINE.json；预检、针对性测试、validate_contract.py |
| A4 | Backend / Agent / Frontend / Map / Data / QA 有写入边界；共享文件唯一写入者；任务卡可直接使用 | DEVELOPMENT.md；人工核对现有目录 |
| A5 | 不增加真实低空承诺、不接入外部 LLM、不更改运行接口、不改变产品验收状态 | diff、契约/数据校验、本轮交接 |

失败边界：本地服务没开时 smoke 应失败并给出地址；缺少高德/ion 配置不伪装在线通过；Schema 漂移不能自动接受；完整聊天缺失不能用推断补成原文。不包含：语音开发、真实运营接入、账户/数据库、部署、付费服务或新的运行时 Multi-Agent 框架。
