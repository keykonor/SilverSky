# WorkBuddy → Codex 修复指令：可用性阻断问题

日期：2026-09-29
依据：`docs/handoffs/workbuddy/2026-09-29-reality-first-validation.md`（P0×1 / P1×5）+ `docs/research/reality-first/UX_2D_REVIEW.md`（24 张截图证据）
性质：**修复指令**。WorkBuddy 已完成定位与方案建议；实现、测试与 Sprint 范围裁定由 Codex 负责。本指令不涉及 Safety Algorithm / JSON Schema / API Contract 变更（F2 若触及 Agent 追问逻辑，由 Codex 评估边界）。

目标：**让用户在结果返回的每一秒都看到与当前方案一致、可信的信息**——这是「能正常使用」的最低线。

---

## F0【P0】地图残留上一城市 —— 必须最先修

**现象**（截图 22/23/24、17）：点「重新规划」换城市后，左侧已显示新方案，右侧高德地图仍显示旧城市街区 4–10 秒，无任何过渡提示。反向同样复现。

**根因**（`frontend/src/components/AmapRouteMap.tsx`）：
1. 路线重绘 effect（L166–269）先 `map.remove(overlays)`，但**地图视野不做任何重置**，旧城市视野原样保留。
2. `setFitView`（L258）发生在**全部坐标转换完成之后**；而 `convertGps`（L43–48）有 ≥1100ms/批的节流，40 点一批。深圳路线约 130 个独立坐标点 → 4 批 × ≥1.1s ≈ 4.4–5.5s 起步，叠加网络往返即实测的 4–10 秒空窗。

**修复要求**：
1. `route`/`origin`/`destination` 变化的第一时间（同步、不等任何异步），进入显式过渡态：显示「地图正在更新…」遮罩或将视野重置为中性状态；**任何时刻不得出现「新方案文字 + 旧城市地图」同屏**。
2. 缩短转换时延（方案由 Codex 定，参考方向）：
   a. 坐标转换前移到规划侧/数据层（快照数据直接存 GCJ-02 或双坐标），前端免转换；或
   b. 转换结果按 `pointKey` 持久缓存（同一点跨方案复用，两城 Golden 大量点重复）；或
   c. 提高批大小/并行批（注意高德坐标转换接口 40 点上限与 QPS）。
3. 转换未完成期间，路线区域**不得**停留在旧城市；可先 `setFitView` 未转换的端点近似视野或直接显示过渡遮罩。

**验收**：跨城市重新规划（深圳→天津、天津→深圳）双向各 5 次，从结果返回到正确城市街区级视野 ≤2 秒，且全程无旧城市地图可见；新增 E2E 回归用例覆盖该序列。

## F1【P1】首次结果返回后 10 秒无路线

**现象**（截图 04/19/20/21）：首次规划结果返回时地图为全国视野（初始化 center [104.2,35.8] zoom 4，L107–109）→ 4 秒时超大视野、起终点 marker 重叠 → 约 10 秒才到街区级。

**根因**：同 F0——全国初始视野 + 转换完成前不 `setFitView`。

**修复要求**：与 F0 同修。结果返回即显示「正在定位路线…」状态文案（`aria-live` 可读），路线就绪前不展示无信息全国图。验收：首结果路线可见 ≤2 秒或全程有明确进度反馈。

## F2【P1】系统无提示接受过去的出发时间

**现象**（截图 09）：审查日 2026-09-29，输入「2026年9月28日15:00出发」直接出方案，无任何「该时间已过去」确认。为已过去的时刻生成出行方案属现实正确性问题。

**修复要求**：解析到 `departure_window.start < now` 时，追问确认（如「这个时间已经过去了，您是指明天 15:00 吗？」）或明确提示后按未来最近同名时间处理。**注意**：涉及 Needs Interpreter / 追问流程，属核心 Agent 边界，具体落点由 Codex 裁定；Golden 夹具中的历史日期属测试数据，需同步评估是否改为相对日期生成。

**验收**：输入过去时间必触发确认或提示；现有 P01–P20 回归与 Golden 夹具同步更新。

## F3【P2】缺「哪个方案更接近现实」的直白结论

**现象**：方案 A 仅「存在限制，已降低推荐优先级」（DOWNGRADE 直译），老人无法据此判断「到底能按哪个走」。

**修复要求**：结果页顶部在现有「没有满足安全推荐条件的方案」声明下，补一句直白对比，例如：「两个方案中，**只有地面方案接近现实出行可参考**（仍需您自行核实入口与交通）；模拟低空方案只是未来演示，现在不能乘坐。」文案需过 Accessibility/ wording 复核。

## F4【P2】福建省边界核验对用户可见

**现象**（L74、L123–142、L293）：「福建省边界查询成功（421 段边界）」常驻地图面板，紫色福建省多边形常驻所有视图，与天津/深圳行程无关，引发「我的路线怎么在福建」的困惑。该探针是 D-014 能力核验证据，不应是产品 UI。

**修复要求**：边界探针与「地图能力核验」面板改为开发模式（如 `?dev=1` 或构建标志）才渲染；生产视图不出现福建省多边形与该文案。保留 `test:amap-local` 的核验路径不受影响。

## F5【P2】「为什么这样规划」机器拼接语

**现象**：「真实天气、可飞条件、运营状态和费用均为 暂无可靠数据。」「步行：暂无可靠数据，未知。」枚举值直嵌句子。

**修复要求**：UNKNOWN 枚举统一映射为自然语言句式（如「暂无公开数据，不代表不可行」），禁止枚举值直接内联；逐条检查解释模板。

## F6【P2，数据层，可与 F0 并行】时长显示与「到达点」证据升级

依据本轮高德实测（`docs/research/reality-first/`）：

1. **时长声明**：OSRM 时长系统性偏乐观 40–45%（TJ 4.7→8.8 min、SZ 11.0→20.1 min）。所有时长渲染必须带「道路模型估算，非预计到达时间」（UI 修复时一并复核显眼程度）。
2. **entr_location 到达点**：高德 `v3/place/detail?extensions=all` 对 4/4 Golden POI 实测返回入口/到达点坐标（证据 `docs/evidence/reality-first/poi-detail-*.json`）。建议评估作为路线端点的「到达点」属性落地，证据等级 MEDIUM，UI 文案写「到达点（未核验具体入口）」，**不得写「入口」**。是否扩 Schema 由 Codex 裁定。
3. **医院子 POI**：总医院门诊楼/地面停车场、北大深圳医院门诊部/急诊部在高德实测存在，可作为 Golden 目的地细化候选。
