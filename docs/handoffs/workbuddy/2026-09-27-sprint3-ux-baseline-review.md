## 总体判断

Sprint 2 PASS 的基础是扎实的：安全结论均有文字表达、医疗急症阻断清晰、无障碍无 serious/critical。但从 UX 基线看，当前页面仍处于"合规审计报告"形态，而非"出行决策产品"形态。四个 P1 问题（REJECT 选中态、枚举暴露、结果首屏不可见、地图标签重叠）都不违反安全红线，却共同决定了一个新用户能否在 30 秒内理解"系统让我怎么办"。Sprint 3 的 UX 主线应当是**重组现有信息的层级与语言**，而不是增加新功能。

## 十项重点检查结论

### 1. 左侧对话 / 需求摘要 / Route Card / Safety / 地图的信息层级

**结论：层级顺序错位，P1。**

现状为单列纵向堆叠：对话（限高 350px 自身滚动）→ 需求摘要 → 规划结果 → 输入框，靠 `step-count 01/03` 暗示进度。三个问题：

- 结果生成后，视口顶部仍是完整对话区和八格需求摘要，Route Card 被推到折叠线以下（`tianjin-ground-map.png` 可证实）。
- 最关键的安全结论——"目前没有满足 SilverSky 安全推荐条件的真实出行方案"（`reference-notice`）——恰恰位于折叠线下方，用户先看到方案卡再看到免责声明，阅读顺序与重要性相反。
- 安全信息分散在三处：顶部 reference-notice、每卡 `safety-line`、底部 `warnings`，无一处统一的"本次规划安全结论"。

### 2. REJECT 方案选中时的"被推荐"误解

**结论：风险成立，建议从 P2 升级为 P1。**

代码证据（`App.css`）：`.route-card.selected{border-color:#417e69;box-shadow:0 0 0 2px #d6e9de}` —— 绿色边框与勾选标记对包括 REJECT 在内的所有方案生效（见 `tianjin-air-map.png`：方案 B"当前不建议采用"，但选中态为绿框 + ✓）。

验收记录 S/P-1 判 P2、Q4 判"不容易发生"的依据是卡内红字与模拟横幅构成第二道防线。本审查尊重该结论但提请注意三点差异：① 30 秒扫视场景下，绿框 + ✓ 是最先被视觉捕获的信号，红色文字是第二位；② 项目红线是"不得宣称真实低空可乘坐"，而 REJECT 卡选中后的视觉状态恰是全页最接近"主推"的表达；③ 比赛演示中讲解员通常会点选低空方案展示地图，正是该状态曝光最高的时刻。选中态语义应为"正在查看"而非"认可"，修复成本低（边框改中性色、✓ 改为"正在查看"文案），收益高。

### 3. 内部枚举暴露（DATA_UNAVAILABLE / SIMULATED_DATA）

**结论：确认存在，且范围大于验收记录，P1。**

`presentation.ts` 已把路线级 `data_status` 映射为中文，但以下后端字符串被原样透传到用户界面：

- `safety_reviewer.py`：`"路段证据包含 DATA_UNAVAILABLE，缺失数据不能被路线级状态覆盖。"`、`"路段证据包含 SIMULATED_DATA，不代表真实可运营服务。"` —— 进入 `risk_assessment.reasons`，显示于**非折叠**的原因列表。
- `candidate_planner.py`：`"DATA_UNAVAILABLE：模拟低空数据文件缺失或损坏；仅保留公开地面候选。"` 等 —— 进入 `result.warnings`，非折叠。
- `solution_synthesizer.py`：`"DATA_UNAVAILABLE，未知。"`、`"全程 DATA_UNAVAILABLE；空中模拟时长不能代表总耗时。"`、`"低空方案为 SIMULATED_DATA，真实运营、地面接驳、天气与价格均未证实；不可预订。"` —— 进入折叠的"为什么这样规划？"。

验收记录 S/P-2 只提"折叠解释仍可见"，实际非折叠的 reasons 与 warnings 同样暴露。对老人而言这些英文大写枚举是纯噪声；对比赛评委而言是"工程半成品"信号。修复方向：在前端建一层 reasons/warnings/explanation 文案映射（或后端改出用户语言版本），**不得删除或弱化"模拟、不可乘坐"的安全语义**，只改表达。

### 4. 用户原始地点与 canonical POI 的关系

**结论：确认成本偏高，P2（对应验收 P-4）。**

需求摘要显示原始输入"天津大学"，地图标记显示"天津大学卫津路校区"，两者关系需用户自行推断。`LocationRef` 已有 `canonical_poi_id`、`entity_precision`、`entrance_verified` 字段，前端类型已定义但未消费展示。建议在摘要的出发地一格内联表达映射："天津大学 → 已定位：天津大学卫津路校区（兴趣点中心，非入口）"，一行文字即可消除歧义，同时把"不是出入口"的免责自然带到。

### 5. 深圳地图标签拥挤

**结论：确认且比记录更具体，P1。**

`shenzhen-air-map.png` 显示右端"目的地·北京大学深圳医院"与"模拟起降点·深圳 Golden Demo 模拟起降点 B"完全重叠不可读；左端出发地两行标签与起降点 A 标签交叠。`tianjin-air-map.png` 同样存在三组标签交叠。三个根因：

- 标签文本为 `角色 · 完整名称`，而模拟起降点数据名称本身含"模拟起降点"，生成"模拟起降点·深圳 Golden Demo 模拟起降点 A"这类自我重复的长串（`RouteMap.tsx` 的 `addMarker` label 拼接 + 数据集命名共同造成）。
- 标签 `pixelOffset` 固定，无碰撞避让。
- Cesium label 无 max-width，长 POI 名不换行。

### 6. 左侧滚动是否影响 30 秒理解

**结论：影响成立，P1（与检查点 1 同根因）。**

以天津地面方案截图实测：首屏只能看到对话 + 需求摘要 + 路线卡标题上方；需要滚动约两屏才能读完两个方案卡、安全原因与规划提醒。30 秒内普通用户能完成的是"看到了对话"，而非"理解了结果"。结果生成时应把视口焦点交给结果区（滚动锚定或需求摘要折叠），否则地图与路线卡的联动设计（切换方案看地图）对不滚动左栏的用户完全不生效。

### 7. Sprint 3 主界面保留 vs 折叠建议

**保留在主界面（一屏内可见）：**

- 统一安全结论横幅（一句话："暂无满足安全推荐条件的真实方案"+ 最重要的一条原因）。
- 两张路线卡摘要态：方案名、时间/步行/费用三项关键指标、安全色条与一句安全结论、选中按钮。
- 需求摘要压缩为单行条（起终点 · 时间 · 行动能力 · 陪同），点击展开完整八格。
- 地图 + 输入框。

**折叠或下放（点击查看全部）：**

- 完整 `reason-list`（保留前 1–2 条在主界面）。
- `warnings` 列表（合并为"3 条规划提醒"入口）。
- "为什么这样规划？" details（含 segment evidence）。
- 对话历史（结果生成后自动折叠为最近一轮）。
- 地图右下浮层中的 OSM 版权、图例与四段免责说明（收敛为"数据说明"折叠面板，保留强制性的模拟警示一行）。

原则：主界面回答"我该怎么办"，折叠层回答"凭什么这么说"。所有安全语义不删除，只调层级。

### 8. 3D 地图扩大后最可能恶化的 UI 风险

按恶化速度排序：

1. **标签重叠**：视角倾斜、POI 密度增大时，屏幕投影重叠呈非线性恶化（现有 P1 在 3D 下会变成不可用）。
2. **双浮层遮挡**：左上 header + 右下 details 两块约 420px 宽的浮层在扩大后的地图上会遮挡更多有效场景，且两者文字量还在增长。
3. **老人相机操作负担**：拖拽/倾斜/缩放的精度要求随维度增加，"空间迷失"（转了一圈不知道自己在哪）对老年用户是真实风险；当前 `flyToBoundingSphere` 动画在 3D 下应提供静止兜底。
4. **晕动**：倾斜视角 + 飞行动画可能引起部分老人不适，需要一个"平面俯视"默认档。
5. **底图真实感差距被放大**：当前无纹理纯色地球在 2D 概览下尚可接受，3D 放大后"空旷色块"与真实城市的落差将成为第一眼印象（依赖数据决策，见检查点 10）。

Sprint 3 若扩大地图，应把"标签碰撞避让 + 浮层收纳 + 相机简化档"作为前置条件而非后补。

### 9. 老人与子女视角：字体、按钮、警示、路线切换

**结论：整体及格有余，字号策略缺失，P2。**

- 字体：正文 16px 基线达到适老下限，但全页混用 13/14/15/16/17px 五档且无规律（eyebrow 13px、辅助说明与图例 14px、解释 15px、正文 16px、急症 17px），小字恰恰承载来源与限制等关键信息。无字号放大开关。
- 按钮：主发送按钮 min-height 48px 达标；demo 快捷按钮 42px 偏小且与主任务视觉竞争。
- 警示：急症面板 17px + `role=alert` 良好；安全结果文字+色块双通道（a11y PASS 结论成立）。
- 路线切换：A/B 卡整体可点、热区充足；但 `✓ / →` 符号语义弱，且选中态与安全语义混淆（检查点 2）。

### 10. 比赛 Demo 视角：最不像"低空综合出行产品"的三个地方

1. **底图是空旷纯色地球**。无影像、无路网、无城市肌理，第一眼更像渲染测试场景而非出行地图。低空出行产品的说服力一半来自"俯瞰城市"的空间叙事，这是当前 Demo 最大的观感缺口（修复依赖底图数据决策 D-00x，非纯 UI 工作，建议提前立项）。
2. **页面读起来像合规审计报告**。六格指标里四格"待确认"，每个模块的主要文字是免责与限制说明，用户全程只获得一个信息："不行"。诚实的边界是项目红线，但表达方式可以反转——先说"我为你确认了什么"（地点已定位、路线已核对来源、安全审查已完成），再说"还差什么"。
3. **"低空"缺乏产品实体感**。模拟低空段只是两段虚线，起降点标签直接暴露工程夹具名"深圳 Golden Demo 模拟起降点 A"，没有任何 vertiport 的场所感（名称、代号、接驳说明）。用户无法从界面感知"这是一个正在成形的出行网络"。

## Top 5 Sprint 3 UX 优先级

1. **重构结果首屏（P1-3 + 检查点 7）**：结果生成后 30 秒内，不滚动即可看到"安全结论一句话 + 两张方案卡摘要 + 地图"。需求摘要折叠为单行条，对话历史自动收纳。这是所有其他改进的容器。
2. **REJECT 选中态去推荐化（P1-1）**：选中 = 查看，不是认可。低成本、高信号，直接支撑比赛演示中最敏感的低空方案讲解环节。
3. **枚举用户语言层（P1-2）**：覆盖 reasons / warnings / explanation 三个透传通道，老人不再读英文枚举；同步补"页面无大写枚举"E2E 断言，防止回归。
4. **地图标签可读性（P1-4 + P2-6 前半）**：短标签 + 碰撞避让 + 起降点显示名清洗，并把这三项列为 3D 扩大的前置验收条件。
5. **canonical POI 关系显性化（P2-1）**：一行"原话 → 已定位 POI（中心点，非入口）"，同时解决确认成本与位置精度免责的传达。

上述五项全部是既有信息的重组与语言转换，不新增产品概念、不触碰安全边界，符合"不设计全新产品"的约束。
